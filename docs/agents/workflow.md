# 工作範圍、協作與文件

開始跨模組任務、安排協作、增修依賴或整理文件時讀本文件。

## 執行流程

1. 核對工作區、分支、status 與相關規格，保留既有未提交改動；先界定本次要完成的使用者行為。
2. 讀相關模組與測試，選擇最小完整變更。若與 SPEC 不同，區分新需求、bug 與文件過時，再更新受影響契約。
3. 實作並按 validation.md 驗證；交付列出成果、證據及有影響的未完成項。
4. 使用者已授權提交時按 commits.md 分批；push、發布或外部 vault 安裝沿用會話的明確範圍。

## 協作與環境

- 只有會話或適用規範明確授權時才派子 agent。需要派工時給定可獨立驗收的工作、路徑 ownership 與依賴，主 agent 負責整合；本文件不新增派工或模型切換授權。
- 同一 checkout 的工作者共享檔案；避免並行修改共用模型、package／lockfile、入口或 build output。需要隔離才用獨立 worktree。
- 依賴變更先檢查現有套件能否滿足需求、Obsidian 執行環境與 API 相容性，再同步更新 lockfile。不為小功能引入與目前規模不符的框架。
- 本機檢查或隔離測試不修改使用者真實 vault、訂閱與外部全域設定。環境阻擋如實記錄，不能把失敗檢查當成功。

## 文件分工

| 文件 | 維護內容 |
|---|---|
| AGENTS.md | 專案方向、全域邊界與必讀路由 |
| docs/agents/ | 現行工作規範；依觸發載入 |
| README.md | 現況、安裝、使用步驟與限制 |
| SPEC.md | 已確認產品契約；新提案與已實作狀態分清 |
| docs/progress.md | 已提交成果與證據入口；只在重要進展更新 |
| docs/*validation*、docs/history/ | 有日期與範圍的驗證證據、歷史計畫 |
| docs/research/ | 外部比較、來源連結、推論與不確定性 |

需求、命令、測試數與版本各保留可追溯來源，減少多份規範重複。更新當前入口時保留歷史記錄的時點；修正歷史錯誤加說明，不偽造當時成果。修改規範後檢查所有相對連結與觸發路由。
