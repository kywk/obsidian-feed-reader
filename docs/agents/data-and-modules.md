# 資料與模組邊界

修改 domain、subscriptions、read-state、cache、feeds、save 或組裝入口時讀本文件，再查 SPEC 對應契約。

## 模組責任

| 模組 | 責任與變更檢查 |
|---|---|
| domain | 共用資料形狀；欄位變更需追查 codec、持久化、UI 與測試使用者 |
| subscriptions | 訂閱解析、驗證、合併與 YAML 寫入；UI 透過服務修改 |
| read-state | cutoff、個別已讀與手動未讀例外；各分類共用來源狀態 |
| cache | 按 vault／來源隔離 metadata 與正文；保留分頁及淘汰界線 |
| feeds | transport、解析與更新排程併發；單來源錯誤隔離 |
| save | 安全 Markdown、模板、筆記身分與檔案追蹤 |
| main／adapters | Obsidian API、依賴組裝及生命週期；核心邏輯可由替代儲存或 transport 驗證 |

沿用這些責任拆分，不為新功能先建未使用的通用層。若需移動 seam，先說明哪個呼叫者因此不必知道實作細節。

## 持久化變更

- 修改 schema 或 ID 前列出現有資料影響、舊資料讀取與必要遷移；只有破壞既有資料時才引入相應版本／遷移，不無條件重建。
- URL 正規化沿用共用規則：query 是來源身分的一部分，title 不是身分；同 URL 的多分類關聯保留。
- YAML／TOML／OPML 都先完成解析與驗證再修改訂閱。外部損壞 YAML 沿用 last-good、停用回寫；不能以空資料覆蓋壞檔。
- 寫入失敗不得宣稱成功。涉及多檔寫入時檢查實際完成範圍與恢復路徑，不假設具備跨檔交易。
- 取消訂閱、快取淘汰與刪分類分別檢查資料生命週期；閱讀狀態與保存筆記的保留依 SPEC，不把它們隨快取一起刪除。
- 修改保存流程時驗證重複保存、檔案碰名、人工修改、rename／delete 追蹤。系統識別 Properties 由系統維護。

## 網路與規模

- 使用現有 transport，保留 timeout、併發限制與同來源請求合併。取消或卸載後延遲結果不可重新寫入已移除的來源。
- 單來源失敗保留既有文章，其他來源可繼續；失敗資訊能定位到來源。
- 列表與未讀統計只取所需 metadata，正文按需取；變更查詢需檢查是否退化為全量正文讀取。
- 跨裝置衝突合併、原文擷取、帳號登入與附件下載均是新產品範圍，不由現有快取或 OPML 功能推定已支援。
